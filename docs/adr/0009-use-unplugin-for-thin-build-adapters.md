# 9. Use Unplugin for thin build adapters

Date: 2026-08-24

## Status

Accepted

## Context

FTS lowering originally served only the editor and exposed Volar mappings. A
project build needs the same proposal semantics as the editor, but bundler
integration should not own proposal parsing or depend on a feature-specific
pipeline API.

Vite does not treat TypeScript returned for an unknown `.fts` extension as a
TypeScript module. The adapter therefore needs to emit JavaScript without
removing ordinary TypeScript as the compatibility boundary established by ADR
2.

There is no single package-naming convention among established build
integrations. [UnoCSS] ships its Vite integration from the product package as
`unocss/vite`. [Tailwind CSS] uses the host-specific `@tailwindcss/vite`, while
[Svelte] calls the same boundary `@sveltejs/vite-plugin-svelte`. [MDX] publishes
separate packages named after each host mechanism, including `@mdx-js/rollup`
and `@mdx-js/loader`. Unplugin's own [plugin conventions] instead recommend an
`unplugin-` prefix and host subpaths such as `unplugin-feature/vite` for packages
that present themselves as Unplugins.

[UnoCSS]: https://unocss.dev/integrations/vite
[Tailwind CSS]: https://tailwindcss.com/docs/installation/using-vite
[Svelte]: https://svelte.dev/packages
[MDX]: https://mdxjs.com/packages
[plugin conventions]: https://unplugin.unjs.io/guide/plugin-conventions.html

## Decision

Expose a feature-neutral core lowering operation that returns ordinary
TypeScript and an encoded standard source map. Derive editor mappings from the
same internal lowering result, while keeping Volar types out of the build-facing
contract.

Use Unplugin for shared host-adapter plumbing and expose only the Vite adapter
as `@ftslang/build/vite` until other hosts have their own conformance coverage.
Use hook-level transform filtering for `.fts` modules and exclude
`node_modules` by default.

Name the product-facing package `@ftslang/build`, not `@ftslang/unplugin`.
Unplugin is an implementation detail that supplies adapter plumbing; it is not
the capability consumers are installing. `build` names the FTS lifecycle
boundary, and the subpath names the host. This also leaves room for a host that
needs a dedicated loader or wrapper rather than an adapter generated by
Unplugin. The package is an integration namespace, not a build CLI or bundler,
and an entry point is public only after that host has conformance coverage.

Pass the ordinary TypeScript intermediate to SWC and compose its map with the
core lowering map using the maintained jridgewell source-map implementation.
The shared transform emits ESM JavaScript instead of depending on any host's
TypeScript handling. Build parse failures remain errors; only the language
plugin may replace an invalid editing snapshot with identity code.

The emitter choice is based on the shared Unplugin transform contract, not on
affinity with the first supported host. Both esbuild 0.28.2 and `@swc/core`
1.15.47 produced executable JavaScript and a composed map that traced the
representative pipeline result to its original `.fts` symbol. On 2026-08-24,
with source maps enabled on macOS arm64 and Node.js 26.1.0, SWC transformed the
98-byte lowered fixture about 9.4 times as fast as esbuild. Across the 14
production TypeScript files then in this repository, SWC was about 5.5 times as
fast. These warm, sequential results were reproduced across three independent
runs with alternating measurement order.

## Consequences

Vite and Vitest can share one adapter without duplicating proposal semantics or
test-runner transforms. The final JavaScript map remains traceable to the
original `.fts` source, and another syntax adapter can be added without changing
the build package.

The build adapter performs a second transform to strip TypeScript and owns SWC
as a runtime dependency. Its transform configuration is larger than esbuild's,
and the tested macOS arm64 native binary was approximately 25 MB instead of 10
MB. Esbuild remains the repository's local package bundler, so this decision
adds another native compiler dependency rather than replacing esbuild
everywhere.

Unplugin can generate other host adapters, but those hosts are not supported
until their behavior and source maps are tested. Extensionless resolution,
semantic checking, formatting, linting, and HMR remain separate decisions.

Consumers do not depend on Unplugin's identity, so replacing the adapter
plumbing does not require renaming the public package. The broad `build` name
also requires restraint: unrelated compiler, editor, formatter, and linter APIs
must remain in their own packages rather than accumulating under this namespace.
